# Post-Hunt Stages Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the `hunt-execution` and `hunt-reporter` skills, a PLAN/RECORD mode split in `hunt-validator`, a hunt-log input to `detection-engineer`, and a new `/run-post-hunt` command, while leaving the six existing artifacts byte-compatible.

**Architecture:** This repo is a Claude Code plugin whose "source" is Markdown prompt content, so there is no compiler or test runner. "Tests" are (a) `grep` assertions that required rules and headings exist, (b) a fenced-block diff proving existing artifact templates did not change, (c) `scripts/validate-frontmatter.sh`, and (d) a dry run of both commands against a scratch copy of the PAN-OS example. Files are the interface between stages: the new hunt log carries a `Results status` field that `hunt-validator` and the others use to decide behavior.

**Tech Stack:** Markdown skills/commands, JSON plugin manifest, bash (`grep`, `awk`, `diff`), `claude --plugin-dir` for the dry run.

**Spec:** `docs/superpowers/specs/2026-10-09-post-hunt-stages-design.md` (read it first; the plan argues from it).

## Global Constraints

Copied from the spec:

- **Additive only.** New skills may write new files. Existing artifacts may not gain, lose, rename or reorder sections or fields.
- **Execution is manual.** No skill runs queries or attack simulations.
- **Grounded in UTH.** Each new element names its UTH step.
- Conventions as in `CLAUDE.md`: files are the interface; one slug per run; annotate gaps with `Unknown` / `[FILL IN: ...]` / `Not provided` / `[PENDING EXECUTION]` instead of inventing content.
- New artifact paths: `./threat-hunting/hunt-logs/<slug>-hunt-log.md`; `./threat-hunting/hunt-reports/<slug>-hunt-report.md` and `.html` twin.
- Hunt log `Results status` values: `PENDING EXECUTION`, `RECORDED`, `PARTIAL`.
- Verdict values: `Supported`, `Refuted`, `Inconclusive`. Disposition values: `True positive`, `False positive`, `Benign`, `Undetermined`.
- `hunt-reporter` section order: Executive Summary → Hypothesis and Verdict → Scope and Coverage Achieved → Findings → Typed Outcomes → Detections → Visibility Gaps → Next Iteration → Metrics → Caveats → Validation → Sources.
- Hunt log section order: Execution Header → Per-Story Results → Hunt-Level Verdict and Coverage → Outcome Candidates → Known-Good / Exclusion List → Deviations and New Questions.
- Untouched files: `skills/gather`, `skills/intel-analysis`, `skills/intel-report`, `skills/hunt-planner`, `agents/intel-researcher.md`.
- In edit instructions below, a backslash before a backtick (\`) is only an escape for this document; write plain backticks in the file.
- Edits to `hunt-validator` and `detection-engineer` must not add or alter any fenced code block (the verification diff compares fenced content exactly). Use prose and tables only.

## Review Focus

Failure modes the spec implies but a casual implementation would miss. Each is pinned by a check in the task that owns it.

1. **Re-run clobbers recorded results.** Re-running `/run-hunt-pipeline` on a slug whose hunt log is `RECORDED`/`PARTIAL`, or whose validation file already holds RECORD content, must leave both untouched. (Task 2, Task 4)
2. **Untriaged hit defaults to benign.** A hit with no disposition must become `Undetermined`, escalate, and block a `Refuted` verdict. (Task 2)
3. **Short window or unconfirmed source reads as "clean."** A window shorter than planned, or a source with unconfirmed events, caps the verdict at `Inconclusive`. (Task 2)
4. **Free-form notes that match no Story.** They go to *Deviations and New Questions* as `Unmapped result`; no Story is guessed. (Task 2)
5. **`hunt-validator` RECORD mode with no detection or no report on disk.** It must skip that write-back and say so, never create the file. (Task 4)

# Hunt Execution Log

A human runs the hunt. This skill records it: it generates the worksheet the hunter fills in, then structures the results the hunter brings back into a hunt log that `detection-engineer`, `hunt-reporter`, and `hunt-validator` can rely on. It never runs a query, never runs an attack simulation, and never invents a result. It implements the Unified Threat Hunting Process's Hunt Execution Steps (Gather and Analyze → Investigate and Validate → Document Observations).

## Step 0: Locate the plan and choose the mode

If the slug is not established from the pipeline or conversation, look for the most recent file under `./threat-hunting/hunt-logs/*.md`, then (if none) `./threat-hunting/hunt-plans/*.md`, and use its slug; if more than one candidate exists, ask the user which one.

Read `./threat-hunting/hunt-plans/<slug>-hunt-plan.md`. It is required: if it is missing, say so and stop, since a log with no plan has nothing to record against. Also read, if present, `./threat-hunting/environment-profile.md` and the existing `./threat-hunting/hunt-logs/<slug>-hunt-log.md`.

| Situation | Mode |
|---|---|
| Invoked as a planning step of `/run-hunt-pipeline`, or the user asks for the worksheet, or no results were supplied | WORKSHEET |
| The user supplies results: the filled worksheet, a file path, or pasted notes | INTAKE |

## WORKSHEET mode

1. **Re-run safety.** If the log exists and its `Results status` is `RECORDED` or `PARTIAL`, do not touch it. Report that results are already recorded and stop.
2. Write `./threat-hunting/hunt-logs/<slug>-hunt-log.md` from the template below, one Story block per `## Story:` in the plan. Pre-fill from the plan: Story ID and title, planned query (the Story's `Detection Logic`), planned window (the Epic's `Scope > Time Window`), data sources and fields, and expected malicious and benign outcomes. Every result field reads `[PENDING EXECUTION]` and `Results status` is `PENDING EXECUTION`. Pre-fill the Known-Good list with any known-good items the plan's Initial Research names.
3. Hand off: give the path, and tell the user to run the hunt in their own tools, record results in the log (or keep notes), then run `/run-post-hunt`.

## INTAKE mode

1. **Read the results** (filled worksheet, file, or pasted text). Keep the hunter's queries verbatim.
2. **Map results to Stories** by Story ID or title. Results that cannot be mapped to any Story go under *Deviations and New Questions* as `Unmapped result` with the original text; do not guess a Story. Stories with no results are `Not executed`.
3. **Check required fields** for each executed Story: queries run, window actually searched, data sources actually queried, result counts, hits, triage dispositions, known-good exclusions applied, deviations. Standalone: ask only for what is missing. When invoked from `/run-post-hunt`: write `Not provided` and do not ask.
4. **Coverage check.** For each data source, record whether it returned events across the whole window searched. Coverage is `Confirmed` only if the hunter says so or shows it; anything else is `Unconfirmed`. A window shorter than the planned window is also `Unconfirmed` for the planned window; record the window actually achieved.
5. **Triage every hit** with one disposition: `True positive`, `False positive`, `Benign`, or `Undetermined`. A hit the hunter did not triage is `Undetermined`. Never default a hit to benign.
6. **Escalate first.** If any hit is `True positive` or `Undetermined`, tell the user immediately, before writing anything else, that this is a potential Suspicious Security Event to escalate to SOC / IR.
7. **Verdicts**, per Story and for the hunt:

| Verdict | Condition |
|---|---|
| **Supported** | At least one hit is `True positive` and bears on the hypothesis |
| **Refuted** | Every Story is `Executed`, coverage is `Confirmed` for every data source over the planned window, and no hit is `True positive` or `Undetermined` |
| **Inconclusive** | Anything else: a Story `Not executed`, coverage `Unconfirmed`, a shorter window than planned, or an `Undetermined` hit. State which |

A clean result is bounded by coverage. Never write "clean" or "no threat"; write "No evidence found in <sources> over <window>."

8. **Set `Results status`:** `RECORDED` if every Story is `Executed`; `PARTIAL` if any Story is `Not executed` or `Partial`.
9. **Outcome candidates.** List each applicable category with an evidence reference:

| Category | Indicated by |
|---|---|
| Visibility Gap | Coverage `Unconfirmed`, a source returned no events, or a needed field is missing or unparsed |
| Security Control Issue | The hunt exposed a control gap independent of detection coverage |
| Detection Opportunity | The query ran, hits were triaged, and the logic could stand as a rule; or the plan expects an Analytics/Detection task and a validated query exists |
| Hunt Opportunity | The hunt surfaced a new hypothesis or question |
| Suspicious Security Event | Any `True positive` or `Undetermined` hit |
| Threat Intelligence Observable | A new indicator or technique not in the intel report |

10. **Known-good.** Record new known-good entries (account, host, process, or pattern, with the reason and who confirmed it) in the Known-Good / Exclusion List so the next hunt can reuse them.
11. Update the log in place and return the path, `Results status`, hunt-level verdict, coverage status, and any escalation.

It implements the Unified Threat Hunting Process's Report & Iterate step and its Maturity & Metrics guidance.

## What this repo is

A Claude Code **plugin**, not an application. There is no build, lint, or test suite. The "source code" is prompt content: skill/command/agent Markdown files that Claude executes at runtime. ## Pipeline architecture

Two commands, split at the point where a **human runs the hunt** (the framework never runs queries or attack simulations):

- `/run-hunt-pipeline` (`commands/run-hunt-pipeline.md`): `gather → intel-analysis → intel-report → hunt-planner → hunt-execution (WORKSHEET) → hunt-validator (PLAN)`
- `/run-post-hunt` (`commands/run-post-hunt.md`), which needs hunt results: `hunt-execution (INTAKE) → detection-engineer (conditional) + hunt-reporter → hunt-validator (RECORD)`

Contracts that span multiple files:

- **Files are the interface.** Stages share no in-memory state. Each reads the predecessor's file and writes its own, under `./threat-hunting/` **in the user's project, never in this repo** (`threat-hunting/` is gitignored). Paths: `environment-profile.md`, `intel-analysis/<slug>-analysis.md`, `intel-reports/<slug>-report.md` (+`.html`), `hunt-plans/<slug>-hunt-plan.md` (+`.html`), `hunt-logs/<slug>-hunt-log.md`, `detections/<slug>-detection.md`, `hunt-reports/<slug>-hunt-report.md` (+`.html`), `validations/<slug>-validation.md`. Renaming a path or section in one skill requires updating every skill that reads it.
- **One slug per run**, kebab-case, ≤6 words, derived by `intel-analysis` Step 0 and reused by every stage.
- **Section order is a downstream contract.** Fixed section orders in the analysis, report, hunt plan, hunt log, and hunt report are read by later stages (e.g. `hunt-planner` consumes the report's `Recommended Actions > Hunt` seeds; `hunt-execution` consumes each plan Story's `Detection Logic`, `Scope > Time Window`, and expected outcomes; `detection-engineer` consumes the plan's Environment Profile and Epic ATT&CK mapping plus the hunt log's executed queries and hit dispositions). Don't reorder or rename them casually.
- **The hunt log's `Results status` drives behavior.** `PENDING EXECUTION` (blank worksheet), `RECORDED`, or `PARTIAL`. `hunt-validator` runs in PLAN mode unless the status is `RECORDED`/`PARTIAL`; `hunt-execution` WORKSHEET mode and `hunt-validator` PLAN mode never overwrite recorded results.
- **Never fabricate, annotate instead.** Gaps become `Unknown`, `[FILL IN: ...]`, `Not assessed`, `Not provided`, or `[PENDING EXECUTION]`. `/run-hunt-pipeline` has no confirmation gates. `/run-post-hunt` has one: it stops if no hunt results are supplied. A true-positive or `Undetermined` hit is escalated before anything else is written.
- **Verdicts are bounded by coverage.** `Refuted` requires every Story executed and coverage confirmed over the planned window; an untriaged hit is `Undetermined`, never benign; reports say "no evidence found in X over Y", never "clean".
- **Two modes for `gather`**: standalone interviews the user; pipeline mode never asks and writes `Unknown`.
- **`hunt-validator` RECORD mode writes back** into the detection's section 9 (if a detection exists) and the hunt report's `Validation` section (if a report exists); the files cross-reference by `DET-XXX` ID.
- **Quality gates** live in skills and their `references/` (intel-analysis rubric READY/LIMITED/INSUFFICIENT with integrity defects overriding score; hypothesis rubric ≥10 with no 1s; GO/CONDITIONAL/NO-GO feasibility; detection robustness on two axes plus a 6-condition acceptance gate). Tune thresholds in the reference file, not by restating them elsewhere.
- **Markdown is the source of truth.** HTML twins for intel-report, hunt-planner, and hunt-reporter are rendered in the same turn from `skills/_shared/references/html-report-shell.md`.
- **Subagent**: `intel-analysis` dispatches four parallel `intel-researcher` agents (`agents/intel-researcher.md`, tools limited to WebSearch/WebFetch/Read/Grep/Glob, returns a fragment, writes no files), one per angle: Actor, ATT&CK/TTP, IOCs, CVEs.

## Conventions

- Skill layout: `skills/<name>/SKILL.md` (frontmatter `name`, `description`) plus `references/*.md` loaded on demand. The `description` is the trigger text, so keep it specific.
- `examples/` holds a sample run for `pan-os-cve-2026-0257`, one file per stage. - `.gitattributes` forces LF on `*.sh`; keep shell scripts LF on Windows.

- The methodology implemented is the [Unified Threat Hunting Process](https://github.com/sims718718/UnifiedThreatHunting). The plugin plans, records, and documents the hunt; executing queries and attack simulations is deliberately left to humans.
